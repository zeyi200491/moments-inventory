# AI 客服知识库导入设计

## 背景

当前 AI 客服工作台已经具备本地知识库存储、知识分层检索、结构化商品库导入、风格样本隔离和前端上传弹窗等基础能力，但这套能力仍然偏底层实现视角，离真实业务使用还差一层“按业务库上传并自动加工”的稳定入口。

本次目标不是重做知识库体系，而是在现有能力之上补齐一层业务导向的导入编排。用户已经准备了 5 类知识材料：

1. 主规则文件，格式为 Markdown，文件内同时包含主规则和 FAQ。
2. 商品库存库，格式为 Excel，内容包含型号、品牌、价格、成本、利润空间、配件、验机视频等。
3. 商品素材库，格式为 Excel，当前主要维护实拍图和验机视频的映射关系，出片图后续再接入。
4. 供应链发货信息库，格式为 Excel，内容包含供应商发货地、快递方式和偏远限制。
5. 风格样本库，格式为 Markdown，只负责语气风格，不参与业务规则。

用户的关键诉求有两个：

1. 知识库上传一次后能够被系统长期记住，后续不需要重复上传。
2. 商品库存库需要支持重新上传，并且每次以上传的最新全量 Excel 覆盖旧商品数据。

## 目标

1. 提供一个面向业务库的统一上传入口，而不是让用户直接接触底层 `knowledge_tier`。
2. 让 Markdown 和 Excel 文件在上传后自动转成适合 AI 检索或结构化选品的数据。
3. 复用当前 SQLite 持久化能力，实现“上传一次即长期可用”。
4. 为商品库存库提供明确的全量覆盖更新链路。
5. 让主规则文件在导入时自动拆分为 `master_rule` 和 `faq` 两层。
6. 让素材库和发货库的 Excel 以“每行一条业务事实”的形式进入知识库，避免整表粗放转文本。

## 非目标

1. 本次不做完整的知识库版本回滚平台。
2. 本次不做多人协作审批流。
3. 本次不做增量商品合并，商品库存只支持全量覆盖。
4. 本次不处理出片图业务，只为未来扩展预留结构。
5. 本次不改变现有知识检索主干策略，只补充导入和管理入口。

## 方案对比

### 方案一：最小改动式导入增强

直接沿用当前 7 层知识模型，只在现有导入入口周围补少量转换逻辑。Markdown 继续走通用导入，Excel 先在前端或后端转文本，再送入现有接口。

优点：

1. 改动最小，落地最快。
2. 风险较低，便于快速验证。

缺点：

1. 主规则拆分和 Excel 映射逻辑容易分散在多个入口里。
2. 后续新增新的 Excel 模板时会不断堆条件分支。
3. 前端仍然需要了解较多底层导入细节。

### 方案二：统一导入编排层

前端只暴露 5 个业务库入口，后端新增一个统一上传编排层。编排层先识别业务库类型和文件格式，再调用对应适配器，把结果写入现有 `master_rule / faq / product_inventory / product_material / shipping_info / style_sample` 体系。

优点：

1. 业务语义清晰，用户只按业务类型上传。
2. Excel 和 Markdown 的转换规则集中管理，后续扩展更稳。
3. 能完整复用当前持久化、检索和商品推荐能力。

缺点：

1. 初次改动比最小增强方案更大。
2. 需要明确定义不同 Excel 模板的列映射规则。

### 方案三：完整知识中心后台

单独建设一个知识库后台，提供上传、预览、差异对比、回滚、启停和版本历史。

优点：

1. 管理体验最完整。
2. 后续多人协作空间更大。

缺点：

1. 周期长，超出当前实际需求。
2. 与当前“先把上传记忆和热更新走通”的目标不匹配。

### 推荐结论

推荐采用方案二，即“统一导入编排层”。它能在不推翻现有知识模型的前提下，把用户的 5 类业务库转成清晰、可维护、可扩展的导入链路，同时满足“上传一次长期可用”和“商品库可全量覆盖更新”的核心诉求。

## 知识库映射设计

本次不新增新的底层知识层，而是将 5 类业务库映射到现有体系中。

### 1. 主规则文件

输入为一个 Markdown 文件，但文件内部同时包含主规则和 FAQ 两类内容。

导入时不应整份按单一层级写入，而应先做章节拆分：

1. 主规则相关章节进入 `master_rule`。
2. FAQ 相关章节进入 `faq`。

这样可以保证：

1. 主规则作为高优先级常驻约束被稳定注入。
2. FAQ 作为补充知识按需召回，不与主规则抢优先级。

### 2. 商品库存库

输入为一个 Excel 文件，包含型号、品牌、成本、售价、利润空间、配件、验机视频等结构化商品信息。

该库不进入普通文本知识库，而继续沿用现有 `products` 结构化商品表。它服务于预算筛货、利润计算、是否有验机视频等规则逻辑，不能退化为纯文本检索。

更新策略明确为：

1. 每次上传最新全量 Excel。
2. 成功解析后全量覆盖旧商品数据。

### 3. 商品素材库

输入为一个 Excel 文件，当前主要维护“型号 - 实拍图/验机视频”的映射关系。

该库导入后应进入 `product_material`，并按“每行一条素材事实”拆分，而不是整表拼成一段大文本。当前版本只要求支持：

1. 实拍图。
2. 验机视频。

后续可在同一结构下扩展出片图、配件图、成色细节图等。

### 4. 供应链发货信息库

输入为一个 Excel 文件，内容包括供应商、发货地、快递方式和偏远限制。

该库导入后进入 `shipping_info`，同样按“每行一条发货规则”拆分。它专门服务于发货、仓库、偏远地区限制等问题，避免与 FAQ 或主规则混用。

### 5. 风格样本库

输入为一个 Markdown 文件，导入后进入 `style_sample`。

这层只影响语气风格，不参与业务规则判断、商品推荐或风险边界。风格学习和业务知识必须保持隔离。

## 上传、记忆与更新流程

### 统一入口

前端工作台中保留一个统一“知识库管理”入口，但用户看到的是 5 个业务库，而不是底层技术字段：

1. 主规则文件
2. 商品库存库
3. 商品素材库
4. 供应链发货信息库
5. 风格样本库

用户选择业务库后，系统再自动限制支持的文件类型和对应的解析方式。

### 上传一次长期记住

知识库“记忆”的本质不是模型记忆，而是导入后的数据持久化存储。所有成功导入的结果都应写入本地 SQLite，并在工作台重开或服务重启后继续可用。

前端应能展示每个业务库当前的入库状态，包括：

1. 是否已上传。
2. 当前文件名。
3. 最近上传时间。
4. 当前条目数。
5. 当前导入状态。

### 非商品库更新策略

主规则文件、商品素材库、供应链发货信息库和风格样本库都允许重新上传，但重传时应按业务库整体覆盖，而不是叠加旧知识。这样可以避免新旧规则并存带来的知识污染。

### 商品库存库更新策略

商品库存库采用全量覆盖模式：

1. 用户上传最新 Excel。
2. 后端解析成功后替换整个商品表。
3. 新商品数据立即参与推荐、利润计算和素材筛选。

不提供增量合并，也不要求用户上传差异表。

## Excel 自动加工设计

### 商品库存 Excel

每行代表一台相机，直接转换为结构化 `ProductRecord`，写入商品表。加工逻辑应包括：

1. 列名标准化，例如“型号/机型”统一为内部模型字段。
2. 价格字段清洗为数字。
3. 视频字段标准化为布尔状态和原始值。
4. 空值兜底，避免脏数据导致整表失败。

这类数据不应再转成普通文本 chunk。

### 商品素材 Excel

每行代表一条素材事实，应转成一条 `product_material` 知识记录。建议最小字段单元包含：

1. 关联型号。
2. 素材类型。
3. 素材链接或说明。
4. 备注。

导入时同时补充标签，如：

1. `model:<型号>`
2. `material:inspection_video`
3. `material:real_shot`

这样后续按“型号 + 场景”召回会比全文检索稳定得多。

### 发货信息 Excel

每行代表一条发货规则，应转成一条 `shipping_info` 知识记录。建议最小字段单元包含：

1. 供应商名称。
2. 发货地。
3. 快递方式。
4. 偏远限制。
5. 补充说明。

导入时补充标签，如：

1. `supplier:<供应商>`
2. `warehouse:<发货地>`
3. `shipping:<快递方式>`
4. `remote:limited`

### 主规则 Markdown 自动拆分

主规则 Markdown 的拆分应基于显式章节规则，而不是依赖模型理解全文结构。建议做法是：

1. 先按标题和段落拆块。
2. 根据 FAQ 关键词识别 FAQ 章节。
3. FAQ 章节写入 `faq`。
4. 其余章节默认写入 `master_rule`。

这样可控性更强，后续调规则也更简单。

## 前端界面设计

### 知识库列表区

前端应展示 5 张业务卡片，每张卡片展示：

1. 当前状态：未上传或已上传。
2. 当前文件名。
3. 最近上传时间。
4. 条目数。
5. 操作按钮：上传或重新上传。

### 上传弹窗

上传弹窗不再让用户直接选择 `knowledge_tier`，而是让用户先选择业务库类型。根据业务库类型限制文件格式：

1. 主规则文件只接受 `md`。
2. 商品库存库只接受 `xlsx`。
3. 商品素材库只接受 `xlsx`。
4. 供应链发货信息库只接受 `xlsx`。
5. 风格样本库只接受 `md`。

上传成功后，应展示：

1. 是否覆盖旧版本。
2. 导入成功的条数。
3. 跳过的行数。
4. 结果提示信息。

### 商品库特殊提示

商品库存库卡片和上传弹窗中都应明确提示：“重新上传会全量覆盖当前商品库”。该提醒属于业务安全提示，必须显式展示。

## 后端接口与编排层设计

### 统一上传接口

建议新增一个统一文件导入接口，例如：

`POST /api/knowledge/uploads`

请求只需要包含两个关键部分：

1. `library_type`
2. `file`

其中 `library_type` 固定为以下业务值之一：

1. `master_rule_bundle`
2. `product_inventory_excel`
3. `product_material_excel`
4. `shipping_info_excel`
5. `style_sample_md`

### 导入编排层

统一上传接口收到请求后，进入导入编排层。编排层根据 `library_type` 分流到不同适配器：

1. 主规则 Markdown 适配器：拆分为 `master_rule + faq` 后覆盖旧数据。
2. 商品库存 Excel 适配器：解析为结构化商品记录并全量替换商品表。
3. 商品素材 Excel 适配器：逐行转为 `product_material` 记录并覆盖旧素材数据。
4. 发货信息 Excel 适配器：逐行转为 `shipping_info` 记录并覆盖旧发货数据。
5. 风格样本 Markdown 适配器：切 chunk 后覆盖 `style_sample`。

### 覆盖逻辑

当前系统的通用文本导入是按 `source_name` 删除旧 chunk，再写新 chunk。这对单文件导入足够，但对固定业务库不够稳。为了避免用户每次文件名不同导致覆盖失效，建议为每类业务库定义固定内部源标识或源分组，例如：

1. `library:master_rule_bundle`
2. `library:product_material_excel`
3. `library:shipping_info_excel`
4. `library:style_sample_md`

重传时按业务库覆盖，而不是按用户上传文件名覆盖。

### 返回结果

上传接口返回至少应包含：

1. `library_type`
2. `status`
3. `replaced`
4. `imported_count`
5. `skipped_count`
6. `message`
7. `uploaded_at`

这样前端可以直接展示“已覆盖旧版本，导入多少条，跳过多少行”的结果提示。

## 容错与版本信息设计

### 文件校验

前端和后端都要做文件类型校验，但以后端校验为准。文件类型规则如下：

1. 主规则文件和风格样本库只接受 `md`。
2. 商品库存库、素材库和发货库只接受 `xlsx`。

### Excel 表头校验

不强制列顺序固定，但必须识别关键列。若关键列缺失，应整次导入失败，不执行替换。

### 行级容错

单行脏数据不应导致整表失败。可修复错误自动清洗；不可修复但不影响整体导入的行应被跳过，并在结果中统计 `skipped_count`。

### 覆盖安全

所有覆盖型更新都必须遵守以下顺序：

1. 先完整解析新文件。
2. 解析成功后再执行删除旧数据和写入新数据。
3. 若解析失败，则保持旧数据不变。

这样可以避免上传失败后把旧知识库清空。

### 当前生效版本信息

每个业务库都应保存一份元信息，至少包含：

1. 业务库类型。
2. 原始文件名。
3. 上传时间。
4. 导入条数。
5. 跳过条数。
6. 导入状态。

第一阶段只维护当前生效版本信息，不做完整历史版本回滚。

## 测试策略

### 后端单元测试

至少覆盖以下场景：

1. 主规则 Markdown 能正确拆分 `master_rule` 和 `faq`。
2. 商品库存 Excel 导入成功并全量覆盖旧商品数据。
3. 商品素材 Excel 能逐行生成 `product_material` 记录。
4. 发货信息 Excel 能逐行生成 `shipping_info` 记录。
5. 风格样本 Markdown 能正确写入 `style_sample`。
6. 文件类型错误和关键列缺失时返回明确错误。

### API 测试

至少验证：

1. 统一上传接口接受正确的业务库类型与文件。
2. 覆盖更新后能返回正确的导入统计。
3. 导入失败时旧数据保持不变。
4. 知识库状态接口能返回当前生效版本信息。

### 前端测试

至少覆盖：

1. 5 张业务卡片的状态展示。
2. 上传弹窗根据业务库切换文件限制。
3. 成功、失败和跳过行提示展示。
4. 商品库存库的全量覆盖提醒展示。

### 集成验证

应补充业务链路验证：

1. 上传主规则文件后，草稿生成能同时命中主规则和 FAQ。
2. 上传商品库存表后，预算推荐使用新商品数据。
3. 上传素材库后，询问验机视频时能召回素材信息。
4. 上传发货库后，询问发货地、快递方式和偏远限制时能命中对应规则。

## 风险与缓解

### 风险一：Excel 模板不稳定

不同来源的 Excel 表头可能不一致，容易让自动映射失效。

缓解：

1. 关键列使用同义词映射。
2. 关键列缺失时直接报错，不做猜测式导入。

### 风险二：旧知识残留

如果覆盖逻辑仍依赖用户文件名，重传不同文件名时可能留下旧数据。

缓解：

1. 使用固定业务库源标识。
2. 所有重传按业务库整体覆盖。

### 风险三：素材和规则串层

若素材库或风格库被当成普通 FAQ 导入，会影响业务决策质量。

缓解：

1. 业务库类型固定映射到底层知识层。
2. 风格样本库继续保持只参与风格，不参与业务规则。

## 验收标准

满足以下条件时，可认为本次设计目标达成：

1. 用户可以在前端工作台按 5 个业务库上传 Markdown 或 Excel 文件。
2. 非商品类业务库上传一次后可长期复用，重启后仍然有效。
3. 商品库存库可以通过重新上传最新 Excel 完成全量覆盖更新。
4. 主规则 Markdown 能自动拆分为 `master_rule` 和 `faq`。
5. 商品素材库和发货信息库的 Excel 能按“每行一条”稳定入库。
6. 前端能够展示当前各业务库的生效状态和最近一次导入结果。
7. 导入失败不会破坏旧数据。

## 结论

本次最合适的落地路径不是重做知识库底层，而是在现有 AI 客服工作台之上补齐“按业务库上传、自动加工、持久化记忆、支持覆盖更新”的导入编排层。

这套方案的核心价值在于：

1. 用户不再需要理解底层知识层和文本导入细节。
2. Excel 数据能被自动加工成 AI 可稳定使用的知识或结构化商品记录。
3. 商品库存库能够以最贴近实际业务的方式持续更新。
4. 系统能长期记住上传结果，并在后续对话和推荐中直接使用。
