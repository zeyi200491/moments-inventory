# CCD 管理操作记录与撤销快照保留策略设计

## 背景与目标

管理员批量操作会保存操作日志和逐商品的新旧值快照，以便查看历史和安全撤销。当前本地 SQLite 和 Cloudflare D1 都没有明确的历史保留上限，快照会持续累积。业务方已确定保留 3 个月；本设计将其定义为滚动 90 天。

目标是在不更改商品当前值、不影响 90 天内撤销能力的前提下，自动删除过期的批量操作记录、撤销快照以及仅服务于这些操作的幂等执行缓存，并让清理具有有界、可重试和可观测的行为。

## 已确认约束

- 本地 SQLite 是库存正式权威源；Cloudflare D1 是发布快照。
- Cloudflare 当前正式写入关闭，但仓库保留批量操作表与恢复机制；维护逻辑仍应正确处理已有记录。
- 来源消失的商品采用标记缺失并人工复核；低置信匹配不自动重绑；这些业务策略不受本功能影响。
- 不触碰真实 SQLite 数据库、Cloudflare 生产 D1、Worker 部署或其他外部资源。
- 保留期为滚动 90 天；UTC 时间戳作为比较基准。

## 方案对比

### 方案 A：两端自动滚动清理（推荐）

本地管理员读取操作历史时执行小批量清理；Cloudflare 复用现有定时维护流程清理 D1。只清理超过 90 天的操作族及其撤销快照，按批次运行，重复调用安全。

优点：符合本地权威库与 Cloudflare 快照两套数据路径；不会依赖管理员手动整理；清理复用现有维护入口。代价：需要分别实现 SQLite 和 D1 的有限批次删除，并补齐本地幂等缓存创建时间。

### 方案 B：仅保留日志摘要，定期清理明细快照

90 天后删逐商品快照，但永久保留轻量日志摘要。

优点：操作列表可长期回溯，空间占用小。代价：与“操作记录和撤销快照保留 3 个月”的决定不一致，记录并非真正按期清理。

### 方案 C：管理员手动清理

提供后台按钮或运维命令，仅在管理员主动执行时删除到期数据。

优点：删除时点可控。代价：容易长期不清理，增加维护负担，也不能落实明确的保留期限。

## 推荐设计

采用方案 A。

### 过期判定

- cutoff 为当前 UTC 时间减 90 天；操作记录 `created_at < cutoff` 才符合过期条件，正好位于 cutoff 的记录暂不删除。
- 撤销操作通过 `parent_operation_id` 归属原操作。一个操作族只有在原操作及所有关联撤销操作都早于 cutoff 时才可清理。
- 若存在 90 天内的关联操作，整个操作族都保留，避免出现看得见撤销记录但找不到原操作、或撤销链断裂的情况。
- 过期操作一旦清理，后台历史列表不再展示；相应撤销不再可用。当前商品价格、可见状态、来源字段和媒体均不修改。

### 本地 SQLite

- 在 `SQLiteShowcaseRepository` 新增可注入时间的清理方法，默认每次管理员读取操作历史时最多处理一小批过期记录；方法使用现有连接锁及事务。
- 分批删除 `showcase_admin_operation_items` 的快照行，再删除日志。历史迁移存在未启用级联删除的表结构，因此实现必须显式删除子行，不能假设外键级联。
- 为 `showcase_idempotency` 增加 `created_at` 字段和迁移；旧缓存回填为迁移时刻，新执行记录写入 UTC 时间。清理 90 天前的批量执行缓存，避免缓存响应长期引用已清理的操作。
- 单次执行设置总删除上限；若某个大操作仍有快照，后续管理员历史读取继续处理。事务中断时当前批次回滚，下一次可安全重试。

### Cloudflare D1

- 扩展现有 `cleanupExpiredEphemeralRecords` 维护操作，使每次定时执行额外清理有限数量的过期操作快照与操作族。
- 使用已有 `created_at`、`parent_operation_id` 索引筛选；先按上限删除快照，再删除无剩余快照且整个操作族均过期的日志。
- 清除已删除操作对应的 `showcase_bulk_operation_owners`（由外键级联）、`showcase_bulk_operation_item_states`（由快照外键级联）、`showcase_bulk_execution_guards` 和 `showcase_bulk_execution_results`。后两者没有对日志的外键，必须显式清理，避免幂等响应引用已不存在的操作。
- 继续通过既有 Cron 维护入口运行；扩大清理结果结构和结构化日志，分别报告删除快照数、操作日志数和幂等/保护记录数。清理失败时不吞掉成功假象，下一次 Cron 重试。
- 不清理预览或会话之外的数据；不调用生产 Worker，也不要求远端 D1 访问。

### 边界与性能

- 每轮有最大行数限制，并使用现有索引避免全表扫描；以明确顺序选择最早到期记录。
- 多个删除阶段在同一个 SQLite 事务或 D1 batch 中提交，避免日志被删除而快照仍孤立。
- Cloudflare D1 批次应避免单条语句超过 SQLite 参数限制；操作族 ID 使用 JSON 参数或受限批次，不拼接用户输入。
- 若数据库状态不满足清理前提（例如孤立快照），方法应保持可诊断并继续安全处理，而不是删除未到期数据。

## 验证设计

SQLite 临时数据库测试：

1. 超过 90 天的操作族和撤销快照被清理；90 天边界和较新的记录保留。
2. 原操作过期但撤销操作较新时，整个操作族保留。
3. 清理不会改写商品现价、可见状态或版本号。
4. 幂等缓存时间迁移、写入、到期清理正确；已有数据迁移后仍可读取。
5. 每次执行受批次上限约束；大批次可通过重复调用最终清空。
6. 事务故障回滚整批，重复清理无害。

D1 仿真数据库测试：

1. 同样覆盖 cutoff、操作族、商品状态不变和幂等引用清理。
2. 检查 FK 级联和显式删除的记录数，确认没有孤立的快照、owner、执行保护或结果。
3. 定时维护成功日志包含清理数量；维护异常会标记失败并能在下次运行重试。
4. 限制每批总删除量，过量数据可跨多个定时周期完成。

## 发布与回退

本任务只实现代码、迁移和文档，不运行生产迁移或部署。部署前需按既有 Cloudflare 发布维护窗口流程，在维护状态下应用迁移、等待定时维护或手工验证、确认清理结果后再开放客户入口。

代码回退时，新增的 `created_at` 列保留（向后兼容）；停止调用清理方法即可停止自动删除。已删除的历史快照不能由代码回退恢复，应依赖现有备份/快照流程，因此上线前需另行确认生产备份可用性；本任务不承诺新的 RPO/RTO。
